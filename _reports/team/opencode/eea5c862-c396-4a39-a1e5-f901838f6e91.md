## 2) السبب الجذري (مُثبت، وليس تخمينًا)

`getSharedPrismaClient()` في `apps/backend/services/sharedDatabase.js:760-821` يُرجِع **Proxy مؤجَّل**:

```js
if (typeof prop === 'string' && prop.startsWith('$')) {
  return async (...args) => {                 // ← يرجع Promise عادي
    await guaranteeConnection();
    return value.apply(sharedPrismaInstance, args);
  };
}
if (prop === '$transaction') {
  return async (...args) => sharedPrismaInstance.$transaction(...args);
}
```

والكود المنشور في `origin/main` لبحث نص الرسائل كان يبني مصفوفة وعود ويُمرّرها إلى `$transaction`:

```js
await prisma.$transaction([
  prisma.$executeRawUnsafe(`SET LOCAL statement_timeout = 5000`),
  prisma.$queryRawUnsafe(query, ...params),
], { timeout: 7000 });
```

Prisma يشترط أن تكون عناصر المصفوفة `PrismaPromise` وليس `Promise` عاديًا، فيرمي **فورًا** على العميل:

> `All elements of the array need to be Prisma Client promises.`

هذا الخطأ **بلا `code`**، ولهذا ظهر في لوج PM2:

```
2026-11-25 03:43:33: ❌ [GET-CONV] message content search failed: SEARCH_ERROR
```

والـController يحوّله إلى `422 MESSAGE_SEARCH_UNAVAILABLE` في ~24ms. كما أن الـProxy ينفّذ `$executeRawUnsafe` و`$queryRawUnsafe` **فورًا** قبل رفض `$transaction`، أي أن استعلام النص كان يعمل غير مُنتظَر (unawaited) بلا فائدة.

**دليل إعادة الإنتاج** (Prisma 6.12.0 + Proxy مطابق لـ`sharedDatabase.js`، نفس الدالة القديمة من `origin/main` مقابل الجديدة):

```
OLD (origin/main, $transaction): ERR name=Error code=undefined ms=15 ::
  All elements of the array need to be Prisma Client promises. ...
NEW (no $transaction): ERR name=PrismaClientInitializationError code=undefined ms=1030 ::
  Can't reach database server at `127.0.0.1:1`   ← تجاوز طبقة $transaction بنجاح
```
كما يُظهر التشغيل نفسه **unhandled rejection** من `$executeRawUnsafe` القديم (نُفِّذ مبكرًا ثم رفضه `$transaction`) — دليل إضافي على أن الـProxy ينفّذ الاستعلامات قبل الرفض.

الأمر: `node proxy_compare.cjs` داخل بيئة اختبار معزولة (Prisma 6.12.0). الملف القديم مُستخرَج حرفيًا من `origin/main`.

> لماذا لم يظهر العيب في اختبار المالك 19/11؟ لأن ذلك البناء كان يستخدم `prisma.message.findMany` (ORM). مسار الـraw CTE + `$transaction` دخل في `9d7bfd922` (24/11 11:11 +0200) وتم نشره في بناء `9693b1997` (24/11 19:32Z).

### 4.1 `conversationSearchWhere.js`
1. **إزالة `prisma.$transaction` نهائيًا** — تنفيذ `$queryRawUnsafe` مباشرة عبر الـProxy (يعمل، ومُستخدم في باقي الكود).
2. **Deadline على العميل:** `Promise.race` مع `SEARCH_STATEMENT_TIMEOUT_MS = 5000` (المؤقت `unref` + `clearTimeout` في `finally` + ابتلاع رفض الاستعلام المتأخر لتجنّب unhandled rejection)، ويُحوَّل إلى `MESSAGE_SEARCH_TIMEOUT` في الـController.
3. **`LIMIT` كعدد صحيح مُضمَّن** (بعد التحقق من السقف 500) بدل `$n` — لا تغيير سلوكي، لكنه يسمح للمُخطِّط بطيّ القيمة.
4. الإبقاء على فلتر المستأجر **داخل** الـCTE وعلى تمرير أخطاء الـDB (من مراجعة gate-4).
5. تصدير `runWithStatementTimeout` لاختبار الـdeadline.

### 4.2 `conversationCrudController.js`
1. `fetchLastInboundMap()` — استعلام واحد `DISTINCT ON ("conversationId")` بدل **N+1** (`findFirst` لكل محادثة) في حساب نافذة 24 ساعة. هذا هو أكبر سبب لزمن 5.5s الذي رصده المالك.
2. `findMany` + `count(total)` + `count(unreplied)` + `count(priority)` في **`Promise.all` واحد** بدل 4 استعلامات متسلسلة.
3. عدّادات التابات صارت على مستوى القناة (`badgeWhere` بدون شرط البحث) — لا تُصفَّر عند البحث، وهو السلوك الصحيح للبادجات.
4. `searchMeta` في الاستجابة: `scope / contentMatchCount / contentSearchMs / contentSearchFailed / contentSearchTimedOut / totalMs` — يتيح قياس الإنتاج من الشبكة بدون DB.
5. **تدهور رشيق**: فشل بحث النص في نطاق `searchScope=all` لم يعد يُسقِط الصفحة بـ422؛ تُعرض نتائج الاسم/التليفون/آخر رسالة + `contentSearchFailed=true`. الـ422 يبقى فقط عند `searchScope=messages` (طلب صريح لنص الرسائل).
6. تسجيل `err.name` + أول 300 حرف من الرسالة (بدل `code` فقط) لتشخيص أسرع.

**أثر الأداء المتوقع:** إزالة N+1 (حتى 50 استعلامًا لكل صفحة) + توازي العدّادات → مسار الاسم يجب أن يهبط من 5.5s إلى أقل من ثانية على نفس بيانات سوان (فهارس trigram على `customers` و`conversations.lastMessagePreview` موجودة أصلًا).

## 7) المخاطر والملاحظات

1. **الـpatch مبني على `9693b1997` (origin/main).** الـHEAD المحلي أقدم من origin/main؛ لا تنسخ شجرة العمل كاملة — استخدم `git apply _reports/team/opencode/eea5c862.patch` على main.
2. **تحذير: لا تُدرِج التعديلات المحلية القديمة** على `scripts/deploy-remote.sh` و`scripts/ensure_trgm_indexes.sql` — نسخة `origin/main` منهما **أحدث وأفضل** (تسقط الفهارس INVALID + `ON_ERROR_STOP` + تحقق)، والنسخة المحلية ستُرجع انحدارًا. الـpatch لا يشملهما.
3. **إزالة `SET LOCAL statement_timeout`:** لم يعد هناك سقف DB من التطبيق؛ السقف الآن على العميل (5s) + فهرس trigram + `LIMIT`. يُنصح بضبط `statement_timeout` على دور/الـpooler (مثلاً 10s) كشبكة أمان، وإلا قد يستمر استعلام شاذ في الخلفية بعد انتهاء الطلب.
4. **`fetchLastInboundMap`** يستخدم `$queryRawUnsafe` عبر الـProxy (نداء مباشر، مسموح) مع `ANY($1::text[])` — نفس نمط `companiesController` العامل في الإنتاج. أي فشل هنا لا يُسقط الصفحة (يُسجَّل تحذيرًا ويعود Map فارغة).
5. **`searchMeta`** إضافة backward-compatible (الواجهة تتجاهل المفاتيح غير المعروفة).
6. **عدّادات التابات** أصبحت لا تتأثر بالبحث — تغيير مرئي مقصود (بادجات صحيحة).
7. **النسخة المحلية السابقة** (من جلسة سابقة، غير ملتزمة) كانت مبنية على HEAD أقدم وتُعيد إدخال انحدار أمني (فلتر المستأجر خارج الـCTE)؛ تم استبعادها والاعتماد على نسخة `origin/main` + الإصلاحات أعلاه. نسخة احتياطية في `%TEMP%\eea5-backup\`.
8. **لا تغييرات frontend / Prisma schema** في هذا الـpatch.
9. **لم يُنفَّذ** أي `git commit` أو `git push`، ولم يبقَ أي ملف في الـindex (استُخدم `git add -N` مؤقتًا لإدراج السكربت الجديد في الـpatch ثم أُلغي)، ولم يُعدَّل أي ملف خارج نطاق المهمة.
